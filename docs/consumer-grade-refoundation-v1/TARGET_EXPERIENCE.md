# Target Experience

## Product-wide rules

Decision-relevant information first; primary actions enter real work context; accepted/interpreted/
pending/saved/failed/ambiguous are different states; healthy automation is quiet; history/provenance
are progressively disclosed; loading/refresh/completion preserve layout and context.

## Mac Today

Persistent primary navigation: Today and Opportunities. Settings/History/support are secondary.

Today composition:
1. compact date/context + Tell PJSDAS;
2. **Now** — one primary executable action with opportunity identity, essential time context,
   concise reason and real action target;
3. a few compact alternatives;
4. **Next** — imminent interviews/tests/deadlines grouped by date with temporal precision preserved;
5. small material automation outcomes;
6. only decisions that block or materially change visible work.

No vanity-statistics/system-health dashboard in the daily first screen. Quiet Today is valid.
Completion updates the affected area without remounting the app or destroying scroll/context.

## Opportunities

Each row answers: which role, current process state, nearest meaningful commitment/deadline and next
useful action/decision. Search/filter/selection/return position persist. Dense workspaces remain
scannable. Wide Mac may use list-detail workspace; narrow layouts use normal hierarchy.

## Opportunity Detail

Order: identity/current state → next node/action → judgment/why → timeline and truly complete/
paginated history → prep/material context → provenance/diagnostics. Mutations occur near the object
they change and return authoritative receipts.

## Tell PJSDAS

Global and context-aware. From detail, current opportunity context is visible.

Feedback is item-specific, e.g. “Recorded: written test completed. Recruiting process remains active.
Undo · View opportunity”. Mixed input reports each clause separately and asks only for missing
distinctions.

Visible lifecycle: `accepted locally → interpreting → awaiting authoritative save → saved`.
Offline/pending never masquerades as server success.

## Decisions

DecisionRequest is a real human judgment, not a system-defect inbox. Present the concrete question,
minimum evidence, recommendation when justified, alternatives and consequences. Technical retries,
cache repair and unrelated-revision merging are system responsibilities.

## Settings

Account; Connections & Automation; Reminders; Preferences; Data & Privacy; Support & Diagnostics.
Do not ask users to choose storage authority or resolve whole snapshots. Connection status reports
usable capability and freshness, not merely “connected”.

## Shared states

Initial loading uses stable skeletons; cached refresh keeps context; offline separates drafts/pending
from saved truth; outcome-unknown queries receipt identity before retry; unrelated conflicts auto
merge; authorization failure shows source/freshness impact; elapsed node stays unresolved without
evidence; account switch never shows/uploads prior-account data.

## Responsive / future iPhone

Contracts remain platform-neutral. CGR certifies responsive Web, not native iPhone. Native work is
reconsidered only after CGR-05 + new owner decision.

## Visual target

Quality is hierarchy, typography, density, alignment, state clarity, accessibility and restraint.
Do not create `AppV9` plus another global polish stylesheet layered over old CSS.
