# Development Plan

## Program shape

This program is fixed to six phases. New numbered CGR phases may not be appended merely because unfinished work is discovered. Scope discovered during execution must be resolved inside the owning phase, explicitly deferred as a non-blocking post-baseline improvement, or escalated as a genuine owner product/value decision.

The program optimizes for user-visible quality increments, not module count.

## Phase sequence

| Phase | Name | User-visible result |
|---|---|---|
| CGR-00 | Contract & Scope Freeze | A single bounded product/architecture/validation authority replaces ambiguous continuation of older roadmaps |
| CGR-01 | Authoritative Command Foundation | Routine connected actions save through explicit authoritative commands with truthful pending/result/undo behavior |
| CGR-02 | Today Vertical Slice | The core daily journey is rebuilt end-to-end on final production architecture and visual primitives |
| CGR-03 | Opportunity Workspace | Opportunities, detail, decisions, prep context, and settings form one coherent daily work surface |
| CGR-04 | Natural Intake & Automation Closure | Web/Gmail/PAIA/current-chat inputs share stronger interpretation, feedback, capability taxonomy, and real end-to-end evidence |
| CGR-05 | Consumer-Grade Certification | Dense real-world use, degraded states, accessibility, cross-device behavior, production canary, and legacy retirement close the baseline |

## Feature-freeze policy

From CGR-00 through CGR-05, no unrelated net-new product feature should be added.

Work is allowed when it is required to make an existing product promise actually complete, replace a weak/legacy implementation, remove maintenance burden, close a reliability/privacy/accessibility/production gap, or provide evidence required by the phase contract.

New external actions, new product domains, and future iPhone work are outside the package.

## Prototype policy

Do not build a complete disposable prototype.

CGR-00/CGR-02 may define high-fidelity reference compositions, interaction rules, component states, and visual baselines. Implementation proceeds directly as production vertical slices using final command/read-model/design-system boundaries.

Exploratory throwaway code is allowed only for a narrowly scoped technical or interaction uncertainty and must not become a parallel product.

## Phase entry

A phase may start only when:

- the prior phase is COMPLETE in STATUS.md;
- the current phase is READY or IN_PROGRESS;
- the owner has explicitly authorized that phase when required by the current execution context;
- remote main and package status have been re-read;
- no higher-priority safety/integrity blocker invalidates the phase.

## Phase completion

Each completion report begins with:

1. what the user can now reliably complete;
2. what previously failed or required maintenance;
3. evidence across continuous journeys, degraded cases, visual/responsive behavior, and production;
4. remaining limitations.

Commit SHA, test counts, CI, and deployment evidence follow afterward.

## Owner checkpoints

Routine owner approval is not required between ordinary implementation decisions.

Owner input is requested only for product-value tradeoffs, irreversible data/permission changes, new cost or paid commitment, privacy/legal boundaries, external consequential recruiting actions, or genuinely different product directions with no objective superiority.

A holistic experience review may be requested at a major production slice boundary, but the owner is not asked to provide pixel specifications or debug lists.

## Program stop

After CGR-05 establishes the stable baseline, stop. Future iPhone work, UU-08 reconsideration, release publication, or feature expansion requires a new explicit owner decision.
