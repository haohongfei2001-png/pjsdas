# Consumer business access, source candidate

This closes consumer access to the existing bounded Prep, independent manual Action and ApplicationGroup reducer. It adds no new entity operations. The owner-only `workspace.manage` version 2 grant, its consent page and its tools remain separate. Legacy grants never qualify for consumer business access.

The new `workspace.business.manage` version 7 descriptor explicitly names bounded reading, reversible writes, conflict-sensitive undo and exclusions. Its exact descriptor hash is `22626aea373e4e8eb51a90ee4b548c5f3aeeee4bbe58e77b418a0645138edb34`. The three new tool names are `get_consumer_business_management`, `execute_consumer_business_management` and `undo_consumer_business_management`. They are registered only through the existing default-off consumer switch and verified audience/account path. A visible tool does not grant permission.

The existing first-party consent page now offers five separate, initially unchanged choices. Business approval requires the consumer switch; exact owned revocation remains available. One transaction checks the account, provider client, request identity, each descriptor/hash and observed grant proof. Five-choice approval/revocation is atomic; a stale proof rolls back the entire batch. Existing owner v2 rows are outside this capability set. A stored grant with a different text hash is displayed as needing new confirmation and remains revocable.

The runtime pins grant ID/revision through reading and final commit. SQL locks the matching version 7 grant, checks the exact hash, then locks the workspace for CAS. Consumer execute and undo use distinct payload-hash namespaces. Both application and SQL replay paths refuse the opposite v2/v7 receipt family, including a command committed while waiting on the workspace lock. The v2 RPC gains only this refusal of newly introduced v7 receipts and undo targets; valid existing v2 behavior is preserved. Undo requires a numeric version 7 business receipt in the current account; compensation comes from that ledger entry. A new service-role-only RPC also checks raw unrelated data, prior history, target before/after evidence and exact collection ordering. Evidence is bounded to 50 unique objects and 1 MiB using the existing exact compact-byte verifier. Per-field value validation, derived-object restrictions and reference reconciliation remain the strict existing reducer's responsibility; this is not a general SQL sandbox. No raw snapshot or grant proof is accepted as a tool argument.

Local evidence: the final full unit suite passed 1,998 tests across 258 files, including both receipt-family replay directions. Actual PostgreSQL passes the fresh beta-account initialize→two-domain consent→read/write/undo→revoke flow, all-five-scope batches and stale-batch rollback; the legacy v2 row is unchanged. Nineteen consumer gateway scenarios cover all nine reducer operations, raw/legacy preservation, newer targets, revocation/CAS, forged legacy proof, wrong grant hash and unrelated/order changes. Independent sessions exercise write-first, revoke-first and regrant-first contention. Additional real SQL cases verify bidirectional execute/undo replay refusal, numeric receipt types, valid retries after fresh regrant and queued same-ID v2→v7/v7→v2 collisions with exactly one ledger entry. The initial source review reproduced an old-v2-result replay in v7; that failing reproduction is retained, and these explicit fences address it. The first new SQL undo attempt exposed an ambiguous receipt column; the qualified ledger reference repairs it, and the passing flow includes undo/replay.

Hosted build, exact-head browser journeys/screenshots, independent source review and dependency adoption remain required. The added browser cases cover explicit mixed business choice and stale-text revocation, alongside the existing eight consumer recovery/navigation/account-switch cases. Local browser launch remains blocked by the executor's socket restriction. This source candidate neither applies a live migration nor changes flags, audience or grants. Fresh-host installation/OAuth/catalog acceptance and public distribution remain separate gates.
