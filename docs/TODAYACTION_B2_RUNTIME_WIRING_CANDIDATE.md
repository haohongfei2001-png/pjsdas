# B2 runtime wiring candidate

Status: production rollout on existing resources is approved as of 2026-10-10, with paid Discovery explicitly OFF. This document is not a deployment receipt. PR #260 remains stacked on #259 until adoption. A17 still requires a real approved complete scope, funding boundary and subsequent scheduler evidence.

## What this connects

The API uses a default-off runtime factory. The existing automation token, current consent generation, authoritative workspace, complete query plan, original claim receipt, CAS and source verification remain required. The existing four query categories cover the full confirmed role/location combinations; a cheap example never replaces the user's scope.

Each original batch claim proposes one immutable USD-micro hold: all its Search requests plus one bounded text inference. The existing Discovery RPC locks the same authority row and workspace, checks prior holds for the account and approval, and records admitted or declined metadata with the original receipt. No additional budget table, editable snapshot cursor, access role or client capability is introduced.

Only the invocation that receives and verifies its own first COMMITTED claim can dispatch. Search and model slots are consumed before awaits; lost acknowledgements, timeouts and unknown provider responses retain the hold. Claims, retries, cadence changes, force and failed/unused slots do not release or reset money. A declined batch has zero retention, settles budget_exhausted and prevents automatic further spending under the same plan. Recovery never overwrites an original admission.

The real AI SDK transport fixes GPT-4.1-mini, only OpenAI routing, plain text, toolChoice none, maxOutputTokens 5000 and maxRetries 0. It has no tools, fallback models, service tier, BYOK, tags or user reporting options. The final current-authority check occurs in SDK fetch after authentication/header preparation. At most one application HTTP dispatch is accepted; redirects fail. These application properties do not prove Gateway's internal billing or team configuration.

## Source-enforced paid-OFF release

The deployed API passes a literal disabled configuration to the runtime factory. Neither an existing environment flag, approval document, credential, scheduler token, manual `force`/`probe`, nor the Cloudflare adapter can activate paid Discovery in this release. The factory returns HTTP 503 with `DISCOVERY_RUNTIME_DISABLED` and `retryable: false` before binding, source, workspace, Search or model calls. Existing account opt-in, cron configuration, user jobs and consent are not changed.

This safely publishes compatible B2 code; it does not enable real automatic search or satisfy A17. Other Web, MCP and Gmail functionality is unchanged. Delegated `ingest_discovery_run` continues to accept separately authorized completed observations, independently fetch source evidence and use the guarded domain commit; it does not invoke the paid search/model runtime. A source fetch is not a paid provider call. The gate applies to this build, not an older independently deployed backend.

Removing the source gate requires a separate reviewed source change and deployment after explicit funding approval, complete confirmed scope, provider/routing/fee verification and required permissions. Unknown or denied deployment configuration is not treated as approved. No restricted configuration access is bypassed. The product self-test recognizes only the exact disabled JSON contract as safe-disabled; this is not evidence of authenticated search success.

## Configuration remains off

With PJSDAS_DISCOVERY_RUNTIME_ENABLED absent or anything other than exact true, the API responds DISCOVERY_RUNTIME_DISABLED before reading bindings, a search key or cloud workspaces. It does not fall back to Sonar or a local result.

Future activation requires an independently approved deployment and existing secure credential setup, plus:

- PJSDAS_DISCOVERY_RUNTIME_APPROVAL_JSON: strict version 1 terms for one account, the complete confirmed scope fingerprint, approval ID, USD maximum, explicit start/end and the fixed tariff version. It also identifies a current funding review, its exact policy fingerprint, and separate billing-boundary and route/add-on evidence references.
- PJSDAS_DISCOVERY_PERPLEXITY_API_KEY: a credential configured through an approved secure handoff. This change creates, stores and transmits no credential by itself.
- Existing Gateway authentication and service-only Discovery authority, with the candidate migration installed after the existing atomic authority migration.

References are identifiers of externally verified evidence, not proof generated by their presence. An arbitrary JSON document or syntactically valid reference does not establish approval, route safety or a financial cap. Production remains blocked until these external facts are verified. No real configuration values or enabled example are included here.

The API ignores other bound accounts, rejects an explicit different account, and disables the unreserved model probe. Funding-review expiry is checked again during authority checks before dispatch. Scope and approval expiry are checked independently.

## Honest cost boundary

The standard direct Perplexity Search request planning amount is 5,000 microUSD, including a successful empty response. The fixed model's single-inference planning envelope is 427,031 microUSD: its published 1,047,576-token context ceiling at $0.40 per million input tokens plus the app's 5,000 output tokens at $1.60 per million, rounded up to a whole microUSD.

For Q queries and M possible model batches, the retained planning amount is 5,000Q + 427,031M microUSD. Complete two-round scope uses both rounds, not only the first tick. If and only if the entire approved scope has four queries per round, two rounds plan eight Search calls and up to eight model calls: $3.456248. This is a planning envelope, not an approved charge and not a demonstrated all-failure-path vendor hard cap.

The public standard model endpoint catalog does not establish whether all Gateway failure handling and team-specific add-ons fit a single inference envelope. Gateway budgets are soft limits. Actual account routing/BYOK/reporting settings and a defensible funding boundary must therefore be verified before activation. No real provider, budget or new service has been enabled.

## Migration and rollback boundaries

The candidate replaces only the body of pjsdas_commit_discovery_workspace_v1 with its existing signature, owner, SECURITY INVOKER and search_path. It fails if that existing function is absent; there is no accidental fresh PUBLIC function grant. No table, role, policy, capability, vault object, credential, cron or grant is added. A partial index over existing account/approval metadata supports bounded admission queries. Existing ACL/RLS/function identity are tested before and after.

Checkpoint preimages remain exact raw authoritative snapshots. Budget metadata is confined to original ledger provenance and receipts. Historical business data, dates, Undo and receipt values are not normalized or migrated. Client-supplied receipt budget metadata is stripped and replaced only by the locked admission decision.

Any future rollback first disables the runtime. Restoring the preceding function body and removing the new index can restore the prior code contract; original claim/receipt rows must remain. Do not discard or reuse old holds, reset an approval, or replay uncertain requests as part of rollback. Production execution requires separate review of current schema/privileges, storage and cost conditions; local PGlite is not that approval.

## Validation limits

Synthetic tests use real schemas/hashes/SDK serialization and injected transport. SQL tests execute the actual migration in PGlite; independent multi-session PostgreSQL 17 tests are a separate required hosted gate. Neither synthetic provider results nor a green protected CI run is A17 real-search acceptance. No user job data, messages or personal links are used in fixtures.
