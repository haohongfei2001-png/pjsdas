# 视觉与交互闭环

## 渲染来源

所有截图来自本包的独立HTML，Chromium 144.0.7559.96，通过Playwright实际运行CSS和JavaScript。不是图片生成，不是生产站点。数据为合成记录。

## 三轮实渲修订

**第一轮 → 第二轮**

问题：两栏底边不平衡；手机“任务6”和“今日任务6”重复；时间窗口挤在窄时间列；岗位库有过大的水平空隙；日程首屏全是历史。

修改：收紧同规格任务行、控制右栏可视高度；窄屏删除重复头部；开放窗口的截止放入主内容；岗位库约束阅读宽度；日程保留全历史但初始定位今天。

**第二轮 → 第三轮**

问题：200%品牌标记裁切；超长岗位仍可能撑高一项；日程初始滚动位置露出上一组的碎边线；追加节点会重新创建早先节点，可能丢焦点；待确认任务错误地提前暗示了一个具体岗位。

修改：品牌使用向量图形、正文仍等比放大；普通列表两行显示与一击详情，大字解除截断；按完整日期组定位；真正追加节点DOM；待确认任务在用户选择前不指定职位。

**第三轮 → 最终交付**

问题：模拟决定任务被过早移除，Undo不能恢复；原本没有结束时间的面试可能被补成一小时；恢复状态的演示撤销按钮需要有可用对象。

修改：收到模拟回执后统一更新任务和日程；不推断缺失的结束时间；保留可补偿的演示状态。重新渲染并复查桌面/笔记本/手机/长内容/大字界面。

每轮对应的源HTML、截图与具体批评在review/。最终截图与RESULTS.json对应同一个HTML摘要。

## 最终观察

- Today 没有单独hero；公司、岗位、时间和动作具有一致顺序，普通内容的六项任务能共同扫描。
- 手机任务/节点切换只控制Today内的两个面板，不增加第四个全局导航。
- 右栏在密集场景实际从10条逐批读到130条已有合成节点，没有重复；滚动没有移动左侧任务。日程“接下来”与此列表的顺序、身份一致。
- 长公司与职位不会在普通字号中把第一项变回hero；完整文字一击可达。200%没有把正文缩回小字。
- 投递入口、投递完成、准备完成、面试参加与改期在演示中保持不同含义。状态恢复只作为界面样例，不算生产可靠性证据。
- 初始验证脚本有两处证据采集错误：在下一帧焦点恢复前立即断言、用“关闭”选中了两个按钮。已保留初始结果并修正采集条件，针对这两项重跑；同一HTML的其余布局与交互结果保留，没有为了通过而改视觉或删除场景。

## 验证范围与边界

实渲包含1920宽屏、1440桌面、1280笔记本、1024/768过渡、390/320手机和实际200%字号；空、单任务、密集、长混排、DecisionRequest、pending、offline、refresh failure、unknown、conflict、loading、无缓存读取失败均有截图。

检查了键盘Tab回绕、Escape与焦点恢复、手机左右键切换、可访问性树。未进行真实屏幕阅读器、手机软键盘、真人理解测试或真实后端调用。不把“无溢出”和脚本通过等同于最终消费产品验收。
